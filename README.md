# Alesinx O-Air BLE

Пользовательская интеграция Home Assistant для локального управления открывателем
окна **Alesinx O-Air** через Bluetooth. Wi-Fi открывателя для передачи команд не нужен.
Интернет используется при получении ключей Smart Life во время настройки.

Версия **0.3.4** описывает все **29 DP** полученной модели Tuya с Product ID
`jjhmwwetqhqa1u3z`: типы данных, права чтения/записи, диапазоны и порядок перечислений.
Есть ограничения обратной связи конкретной прошивки — см. раздел ниже.

## Установка и обновление

### Через HACS

1. В HACS откройте **Пользовательские репозитории / Custom repositories**.
2. Добавьте `https://github.com/eldarsudden/o-air-ble`, тип **Интеграция / Integration**.
3. Откройте **Alesinx O-Air BLE** и загрузите последнюю версию из ветки `main`.
4. Перезапустите Home Assistant, затем добавьте интеграцию в **Устройствах и службах**.

Если HACS ранее отказал при загрузке `748b801`, обновите информацию о репозитории
и выберите новый коммит: в старом ещё нет файла `hacs.json`.

### Вручную

1. Скачайте репозиторий через **Code → Download ZIP** и распакуйте его.
2. Скопируйте `custom_components/alesinx_ble` в каталог конфигурации HA:
   `/config/custom_components/alesinx_ble`.
3. Перезапустите Home Assistant. Зависимости Python установятся автоматически.
4. Убедитесь, что настроен **Bluetooth**, а адаптер находится рядом с открывателем.
   Прокси Bluetooth должен поддерживать активные соединения.
5. Откройте **Настройки → Устройства и службы → Добавить интеграцию →
   Alesinx O-Air BLE**.

Для обновления замените весь каталог компонента и перезапустите HA.
Уже созданные записи сохраняются; новые сущности добавляются автоматически.

## QR-вход и несколько окон

1. Выберите **Войти через QR Smart Life**.
2. Укажите телефонный код страны (например, `7`) и регион аккаунта:
   `eu` — Европа, `us` — Америка, `sg` — Сингапур, `cn` — Китай, `in` — Индия.
3. Отсканируйте QR сканером Smart Life и подтвердите вход.
4. Нажмите **Продолжить** в HA.
5. Выберите открыватель и закройте Smart Life, чтобы освободить Bluetooth.
   HA получит localKey/secKey выбранного окна и проверит BLE без движения.

Один установленный компонент обслуживает несколько открывателей. Каждый добавляется
отдельной записью с собственными ключами, сущностями и настройками. Для следующего
окна снова добавьте интеграцию и повторите QR-вход.

Пароль, User Code и ручной ввод ключей не нужны. Подтверждение QR принимается
в течение трёх минут. Если время истекло, отметьте **Создать новый QR-код**
и нажмите **Продолжить**.

Ключи запрашиваются только для выбранного O-Air. Облачная сессия и QR-токен
не сохраняются; сессия очищается при завершении или отмене мастера. Устройство
остаётся привязанным к Smart Life. Адрес Bluetooth с Mac переносить не нужно:
поиск выполняется по заводскому UUID.

Сохранённый JSON тоже можно импортировать. Принимается объект с полями `device_id`,
`uuid`, `local_key`, `sec_key` и необязательным `name`, либо массив таких объектов
в поле `devices`.

## Чтение, запись и обратная связь

O-Air надёжно отвечает на **отдельные запросы каждого DP**. Пустой общий запрос
и запрос списка DP не дают полного набора значений. Поэтому интеграция опрашивает
параметры по одному раз в минуту. В проверке устройства прочитаны 28 из 29 DP;
DP 118 не вернулся и отображается как `unknown`.

DP 101, 110, 119 и 131 передаются как числовые перечисления. Их порядок сверён
со схемой Tuya; он различается у команды окна и действия сценария.
Числа и логические значения записываются с соответствующими типами KLV.

**Нулевое подтверждение BLE означает приём запроса модулем и не доказывает
применение настройки.** После записи интеграция читает параметр обратно. Если
он отличается от отправленного, повторяет только чтение и сообщает об ошибке
проверки. Запись автоматически не повторяется. В атрибутах сущности доступны:

- `last_acknowledged_value` — значение отправленной и принятой BLE-команды;
- `last_write_verified` — совпало ли оно с результатом чтения (`null`, если ответа нет);
- `value_reported` — получено ли значение от устройства.

На проверяемом устройстве наблюдались прежние значения после подтверждённых
команд: Opening limit оставался 9 после отправки 10; DP 119 и DP 132 не менялись
после движения. Это повторялось и после переподключения BLE. Поэтому применение
всех настроек и актуальность всех показаний конкретной прошивки ещё не подтверждены.
Интеграция показывает прочитанные значения и не подменяет их отправленными.

## Положение окна

DP 132 вернул `0` у физически открытого окна. Его шкала не используется как
нормализованный процент положения в карточке окна HA. Значение доступно отдельным
сенсором; произвольная установка позиции не предоставляется.

Состояние окна определяется по DP 119. Если полученный режим противоречит последней
команде движения, состояние считается неизвестным до подходящего ответа устройства.
Старый режим OPEN после команды CLOSE не используется как подтверждение открытого окна.

## Соединение и диагностика

Соединение открывается на время операции и затем освобождается. Операции одного
окна выполняются последовательно. Команда движения не повторяется при потере
подтверждения. Ошибка последующего чтения не превращает принятую команду движения
в команду, которую нужно повторить.

Если соединение не устанавливается, закройте Smart Life, проверьте расстояние до
адаптера и повторите попытку. При необходимости отключите Bluetooth телефона.

Первый запуск проверяет подключение и ответ на авторизованный запрос состояния,
затем создаёт сущности. Полный опрос 29 DP выполняется в фоне; до получения ответов
значения могут быть неизвестны. Проверка запуска ограничена 45 секундами плюс
время освобождения соединения (до 10 секунд на отключение). При неудаче HA повторяет
запуск, а журнал содержит `O-Air initialization failed during ...` с этапом:
`discovery`, `connecting`, `subscribing`, `device_info` или `reading_state`.

Если журнал пуст, включите отладку в меню интеграции или добавьте в
`configuration.yaml` (объедините с существующим разделом `logger`, если он есть):

```yaml
logger:
  logs:
    custom_components.alesinx_ble: debug
```

После перезапуска ищите `O-Air` в **Настройки → Система → Журналы**.
Начало и завершение запуска записываются на уровне INFO, ошибка запуска — WARNING.
Эти сообщения содержат этап операции, без ключей и содержимого BLE-пакетов.

### Если открыватель не найден при настройке

После QR-входа отключите Bluetooth телефона и повторите выбор открывателя в мастере.
Smart Life может занимать BLE-соединение, пока приложение работает.
Адаптер рядом с окном должен принадлежать Home Assistant: Bluetooth на Mac,
использовавшийся для диагностики, не передаёт данные на другой сервер HA.

В [мониторе рекламы Bluetooth](https://my.home-assistant.io/redirect/bluetooth_advertisement_monitor/)
проверьте наличие `TUYA_` с сервисом `0000fd50-0000-1000-8000-00805f9b34fb`.
Для извлечения заводского UUID нужен ответ на активное сканирование. Если сканер
принудительно переведён в пассивный режим, включите активное сканирование в настройках
адаптера. Интеграция отслеживает ответы во время поиска и проверяет данные от всех
доступных источников, а не только запись от адаптера с лучшим сигналом.
Данные для определения UUID могут прийти и от приёмника без поддержки соединений;
подключение всё равно выполняется через доступный для того же адреса адаптер
с поддержкой соединений. Если запрос активного сканирования HA завершается сразу,
интеграция продолжает ждать рекламу до окончания заданного времени поиска.

Ошибки мастера различают отсутствие сканера, отсутствие источника с поддержкой
соединений и неполные данные Tuya. В журнале строка `O-Air discovery:` содержит
число сканеров, источников с поддержкой соединений, устройств FD50 и декодированных
UUID. Ключи, UUID и содержимое рекламы в этой строке не выводятся.
`target_matches` показывает, сколько декодированных UUID совпало с выбранным окном:
наличие второго O-Air само по себе не означает, что найден нужный.
При ошибке дополнительные строки `O-Air advertisement:` содержат Bluetooth-адрес,
RSSI, длины данных, результат сопоставления UUID и наличие адреса в истории
источников с поддержкой соединений. Сами UUID и ключи в журнал не записываются.

Отдельная команда обычной перезагрузки не обнаружена. Значение REBOOT у DP 131 —
событие только для чтения. Сброс устройства и удаление привязки интеграцией не выполняются.

Проверки выполнялись на Home Assistant **2026.9.0** и **2026.10.4**, Python **3.14.10**, Bleak
**3.0.2**, с двумя O-Air. Автотесты проверяют типы и диапазоны DP, порядок перечислений,
форматы BLE, QR-вход, проверку чтением и обработку неизвестных значений.
Работа через ESPHome proxy и полный QR-вход через браузер на сервере HA владельца
отдельно пока не проверялись.
